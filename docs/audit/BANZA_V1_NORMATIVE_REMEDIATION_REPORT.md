> **Decision — closed.** BANZA `protocol_version` is **1.0.0** and does not change in this milestone.
> This is a project decision, not an open question: 1.0.0 is pre-production — no production operator,
> no active technical certification, no real money, no external production consumers — and the evidence
> shows `BCJ/1` produces identical bytes for the artifacts currently emitted, with existing signatures
> still valid. Making a previously implicit rule explicit is completion of the 1.0.0 surface, not a new
> version of it. `BCJ/1` carries its own identifier so canonicalization can evolve without touching
> `protocol_version`. **No alternative version is proposed anywhere in this document.**

## 1. Material decisions

### D-1 · The protocol version does not change (ADR-081)

`protocol_version` stays `1.0.0`. No production contract changes its wire shape; what changed is that a
previously unpublished rule became published. Canonicalization is versioned **independently** as `BCJ/1`,
so a future change to it can be versioned precisely without moving the protocol version.

### D-2 · Canonicalization is RFC 8785 restricted by a BANZA profile (ADR-082)

**PROFILE RFC 8785**, not bare adoption and not a bespoke scheme. The profile — integers only within
±(2⁵³−1), duplicate members rejected, unknown members preserved, no Unicode normalisation, UTF-16 member
ordering — is what makes a standard designed for general JSON safe for a protocol that carries money.

The decisive profile rule is **P1 (integers only)**: it removes ECMAScript double formatting, which is the
largest source of cross-language divergence in RFC 8785. This was not a convenience choice — it was
verified first that **zero** `type: number` fields exist in any signed-artifact schema and that BANZA
already mandates integer minor units.

### D-3 · Measured migration impact: none

ADR-081 initially assumed publishing the rule would change bytes and force regeneration of every signed
artifact. **That assumption was tested and is false.** `BCJ/1` and the prior reference behaviour coincide
for every artifact BANZA produces, because they all use ASCII member names, integers in range, and no
floats.

Evidence — `engines/banza-trust/tests/canonical_migration.rs`:

- byte-identity asserted across signed protocol metadata, trust root metadata, operator manifest,
  conformance evidence, public registry entry and the BRL;
- **a signature produced under the prior behaviour still verifies under `BCJ/1`** — which it can only do
  if the signing bytes are unchanged;
- the live Operator Zero artifact was checked independently: 19 members, all-ASCII names, all integers
  within the safe range.

No artifact required regeneration. The transition is a specification change, not a data migration.

## 2. Cryptographic impact

| Aspect | Before | After |
|---|---|---|
| Rule location | `engines/banza-trust/src/lib.rs` (`serde_json::to_string`) | `spec/canonicalization.md` (normative), implemented by the engine |
| Language coupling | Total — the norm was one crate's serializer | None — the rule is text, with vectors |
| Member ordering | UTF-8 byte order (incidental `BTreeMap` default) | UTF-16 code units, stated (P6) |
| Numbers | Whatever `serde_json` emits (`100.0`, `1e+22`) | Integers only, safe range, rejected otherwise (P1/P2) |
| Duplicate members | Parser-dependent (last-wins) | Rejected, fail-closed (P3) |
| Unknown members | Undefined | Preserved and signed (P4) |
| Unicode | Undefined | Not normalised; publishers emit NFC (P5) |
| Bytes produced for real artifacts | — | **Identical** (§1 D-3) |

**Cross-implementation evidence.** The public vectors were generated by an implementation written from the
specification text, with no shared code with the engine; `engines/banza-trust/tests/canonicalization_vectors.rs`
asserts the Rust engine reproduces all 24 (15 accept + 9 reject) exactly, including the digest and byte
length of each. Two independent implementations agreeing is the evidence that the rule now lives in the
specification rather than in either implementation.

## 5. Remaining work, with rationale

Four findings are deferred rather than closed, and each is deferred for a stated reason rather than for
convenience:

- **F-05 (reason codes)** and **F-06 (idempotency)** both require a *scope decision first* — the milestone
  itself (§24) requires classifying each subject as protocol-normative, profile-normative, Layer 3, or
  implementation-internal before specifying it. Specifying them without that classification is exactly the
  "import requirements from other systems" failure the milestone forbids.
- **F-07 (semantic equivalence)** is now half-closed: the digest-level foundation is specified and
  vector-backed. The field-level rule depends on F-05, because "equivalent reason codes" cannot be defined
  before the reason-code model is.
- **F-08 (trust-plane origin)** is a genuine architectural decision, not a documentation gap. The milestone
  (§36) explicitly permits recording it as a future consideration rather than implementing federated
  distribution because it is possible.

These are the substance of the next milestone. **The audit's P0 is closed and does not reappear in it.**

## 6. Final verification pass

A second pass audited the remediation itself rather than the audit's findings: manifest scope,
classification, `BCJ/1` internal completeness, extensibility closure, vector independence, hash
integrity, and any remaining code-as-authority. It found **seven defects, all in work this milestone
had produced or claimed to have closed**, and closed each of them.

### 6.1 Defects found and fixed

| # | Defect | Why it mattered | Fix |
|---|---|---|---|
| **V-1** | `canonical_bytes` collapsed every BCJ/1 rejection to an **empty byte vector**, and `verify_signed_doc` / `canonical_sha256` then operated on it | Not fail-closed, and worse: every rejected artifact produced the *same* signing input and the *same* digest. Two different invalid documents shared one signature target. The specification says reject; the implementation degraded | `canonical_bytes` and `canonical_sha256` now return `Result`. All 20 call sites across five crates handle rejection explicitly; verification paths fail closed. Spec §7 step 1 states that rejection is not degradation |
| **V-2** | **P3 was unreachable on the production path.** `verify_signed_doc` takes a parsed `Value`, and by then `serde_json` has already resolved the duplicate (last-wins) | Duplicate-member signature confusion is exactly what P3 exists to close, and it was not being closed for real traffic | Added `verify_signed_doc_bytes`, which applies P3 to the wire text before parsing. The spec now states that P3 is observable only on the bytes, and that a verifier receiving bytes MUST apply it before parsing |
| **V-3** | `engines/banza-root-ceremony` carried its **own canonicalization** (`serde_json::to_vec`) — the pre-remediation behaviour — and signs trust root metadata, which `BCJ/1` §6 covers | The claim "the reference implementation implements the specification" was not true repository-wide: a second engine still defined its own bytes | It now delegates to `banza_trust`. A cross-engine parity test pins it. Its 17 tests pass unchanged, which is additional evidence of byte-identity |
| **V-4** | Four production schemas declared `"_authority": "engines/banza-certification"` | The same inversion as F-04, in a differently-named field the F-04 guard did not cover | All four rewritten to name the ADR and the schema as authority and the engine as implementation. The guard now holds `_authority` to the same standard as `_source_of_truth` |
| **V-5** | `conformance/manifests/schema.json` and `conformance/capabilities/schema.json` were **absent from the manifest**, although Open Trust Evaluation check `valid_operator_manifest` validates against the first and `federation-manifest.json` extends it | The manifest claimed to identify the normative surface while omitting a schema a normative check depends on | Both added as `NORMATIVE_SCHEMA`, tier `implementation` |
| **V-6** | Six `spec/**` documents self-declare **Canonical** or **Normative** and carry implementable requirements — transport rules, per-interaction re-evaluation, atomicity, freshness windows, the routing idempotency key format — and none was in the manifest | Under-inclusion is the same defect as over-inclusion: the manifest was not the surface | All six added as `NORMATIVE_SPECIFICATION` |
| **V-7** | `contracts/events/types.json` pointed at `contracts/webhooks/event-types.json`, which does not exist | A dangling pointer of the same class as F-04 | Corrected to `contracts/events/webhook-types.json` |

ADR-082's *Consequences* section was also corrected: it still asserted that bytes change for every
signed artifact and that artifacts must be regenerated. Measurement disproved that, and ADR-081 had
already been corrected; ADR-082 had not.

### 6.2 Manifest scope and classification

The manifest went from 130 entries with a `kind` label to **138 entries with a two-axis
classification**. The second axis is what answers the question that matters:

| tier | count | meaning |
|---|---|---|
| `implementation` | **82** | An independent implementation MUST satisfy this. **This is the clean-room reading list.** |
| `conformance` | **51** | Material for *demonstrating* conformance. Expresses requirements defined elsewhere; on conflict the contract governs and the vector is a defect |
| `legal` | **3** | `LICENSE`, `NOTICE`, `TRADEMARKS.md` |
| `informative` | **2** | Published and stable, imposes no obligation |

**Being listed is no longer the same as being required.** Three artifacts were audited individually
and demoted on the evidence of their own text:

- `contracts/openapi/reference-operator.yaml` → `informative`. Its own words: *"This is not a
  production API. All state is in-memory and resets on restart."* It is the L0 sandbox of the
  reference implementation.
- `contracts/openapi/operator-validation.yaml` → `informative`. Self-declared *"reference/documentary
  contract"*.
- `contracts/openapi/interoperability-certification.yaml` → `conformance`. The certifying side's
  read-only publication surface; no operator implements it.

Four OpenAPI surfaces remain `NORMATIVE_API`, and each says so itself: activity, collections,
transfers and wallet-onboarding are marked *"operator-implemented surface"* or *"operator-AGNOSTIC
protocol surface … what every BANZA operator MUST expose."*

**One divergence is recorded rather than silently resolved.** Seven production schemas are required
for implementation but declare `"_status": "reference"`. The manifest now records each artifact's
`self_declared_status`, so the divergence is visible; the guard freezes it at seven so it cannot grow.
Resolving it is audit backlog **P2-6**, deliberately not reopened here.

### 6.3 ADRs and RFCs are not on the reading list

No ADR and no RFC is in the manifest, and `not_normative` now says so in those words: *"No ADR is
required reading to implement BANZA 1.0.0"* and *"every BANZA RFC is Draft and none is a requirement
of 1.0.0."*

The Draft question was tested rather than assumed. Six BANZA RFCs exist, all Draft. Four federation
contracts name one in `_authority`:

| Contract | Names | Does 1.0.0 depend on the Draft? |
|---|---|---|
| `federation-routing.json` | RFC-0001 | **No** — the fields, the `rr-<uuid>` idempotency key and the invariants are in the contract and in `FEDERATION_CONTRACT_SURFACE.md` |
| `federation-obligation.json` | RFC-0002 | **No** — obligation structure is in the contract; RFC-0002 is cross-operator settlement, an L4 subject 1.0.0 does not require |
| `federation-manifest.json` | RFC-0002, RFC-0005 | **No** — the manifest extends `conformance/manifests/schema.json`, which is now in the manifest |
| `federation-trust.json` | RFC-0005 | **No** — the reference is descriptive ("the RFC-0005 discovery manifest at `/.well-known/banza/operator.json`"); the path and schema are published in eight `tier=implementation` artifacts |

**No Draft is a normative dependency of 1.0.0.** What the four citations show is a naming defect —
`_authority` should name Accepted authority, not a Draft — recorded for the next milestone and not
fixed here, because fixing it means deciding each RFC's disposition, which is architecture.

### 6.4 `BCJ/1` internal completeness

Checked point by point. Every item is stated in the specification and pinned by a vector, a unit test,
or both.

| Property | Where | Vector |
|---|---|---|
| Integers only, permitted domain | §3 P1 | BCJ-003, BCJ-014; BCJ-R01, BCJ-R02 |
| Integer bounds ±(2⁵³−1) | §3 P2 | BCJ-004, BCJ-005; BCJ-R03, BCJ-R04 |
| Member ordering, UTF-16 code units | §2.2, §3 P6 | BCJ-001, BCJ-012, BCJ-013 |
| Duplicate members rejected | §3 P3 | BCJ-R05, BCJ-R06, BCJ-R09 |
| Unknown members, unambiguous treatment | §3 P4 | BCJ-007, BCJ-015; BCJ-R07, BCJ-R08, BCJ-R09 |
| Strings and escaping | §2.4 | BCJ-006 |
| Unicode, no normalisation | §3 P5 | BCJ-008 / BCJ-009 (same text, different digest) |
| Arrays (order preserved) | §2.3 | BCJ-002 |
| Objects, `null`, booleans | §2.5 | BCJ-010, BCJ-011 |
| UTF-8 output; input form | §2.1, **§3 P8 (added)** | all |
| Canonical bytes / signing input | §4 | — |
| Hashing input | §5 | digest on every accept vector |

Two gaps were found and closed in the specification text itself:

- **P8 (new)** — a canonicalizable artifact MUST be a top-level JSON **object**, in well-formed UTF-8;
  text that is not well-formed, not valid UTF-8, or carries an unpaired surrogate MUST be rejected and
  MUST NOT be repaired or substituted. §4 presupposed an object without saying so, and invalid-Unicode
  handling was unstated.
- **§7 step 1** now states that rejection is not degradation, and where P3 must be applied.

`-0` was checked explicitly: the spec rejects it and the implementation rejects it (P1).

### 6.5 Unknown fields cannot bypass `BCJ/1`

The question is whether extensibility is a hole. **It is not**, and this is now both specified and
tested rather than merely true by accident of implementation.

P4 was rewritten to say it outright: *"Extensibility does not relax any rule… an artifact MUST be
rejected if an unknown member — or anything nested inside one, including inside arrays — carries a
fractional or exponent number, an integer outside the P2 range, or a duplicate member name."*

Six tests in `engines/banza-trust/tests/canonical_profile_closure.rs` pin it: fractional, exponent,
out-of-range at both bounds, nesting through objects and through arrays, duplicate inside an unknown
member, and the positive case (a conforming extension is preserved and sorted into canonical
position). Four public vectors — BCJ-015, BCJ-R07, BCJ-R08, BCJ-R09 — carry the same property to any
third-party implementation.

### 6.6 Vector independence

The chain is specification → public vectors → independent implementation → reference verification, and
it is intact:

- The vectors were computed by an implementation written from `spec/canonicalization.md` alone, sharing
  no code with the engine.
- The vector file carries the expected canonical form, byte length and SHA-256 **as committed data**.
  `canonicalization_vectors.rs` compares the engine against those committed values; it does not compute
  the expectation at test time, so the engine cannot define its own pass condition.
- The four vectors added in this pass were computed the same way, and the independent implementation
  was asserted to *reject* each reject-vector for the stated rule before the vector was written.

24 vectors: 15 accept, 9 reject.

### 6.7 Manifest hash integrity

The manifest is a verifiable identification of the surface, not a list, and the guard proves it on
every run rather than asserting it:

| Property | How it is verified |
|---|---|
| No inconsistent self-reference | The generator excludes the manifest from itself; the guard rejects a manifest that lists itself |
| All SHA-256 recomputed | Every artifact is re-hashed from disk and compared |
| A removed artifact fails | Self-test constructs that case and asserts detection |
| A modified artifact fails | Self-test substitutes a wrong digest and asserts detection |
| A non-existent path fails | Self-test appends one and asserts detection |
| Generation is deterministic | The guard regenerates and requires the result to be byte-identical |

| Capability | Verdict | Basis |
|---|---|---|
| Canonicalization | **YES** | `spec/canonicalization.md` + 24 vectors |

| Hashing | **YES** | §5 + §6 exclusion table + a digest on every accept vector |

For the next milestone, **BANZA v1.0.0 — Execution Semantics & Protocol Contract Completion**. This

### X-04 — Reason codes

**Where they appear, and which are already closed:**

| Surface | Field | State |
|---|---|---|
| `certification-record.production.schema.json` | `reason_code` | **CLOSED** — 18-value enum |
| `revocation-entry.production.schema.json` | `reason` | **CLOSED** — 7 values |
| `root-revocation.production.schema.json` | `reason` | **CLOSED** — 4 values |
| `contracts/federation/revocation-list.json` | `revoked[].reason` | **CLOSED** — 2 values |
| `federation-trust.json` | the 13 OTE check ids | **CLOSED in the contract** — every check has a published id |
| `federation-trust-evaluation.production.schema.json` | `failed_checks` | **OPEN** — free string array, although the values it can hold are the 13 ids above |
| `journey-receipt.production.schema.json` | `reason_codes` | **OPEN** — free string array |
| `operation-receipt.production.schema.json` | `reason_codes` | **OPEN** — free string array |

**Layer ownership, as the evidence stands:**

- *Conformance* — the certification vocabulary is already closed and belongs to Layer 2.
- *Execution* — the receipt vocabulary is the open one. Receipts are produced per operation.
- *Certification* — consumes reason codes but does not define them.
- *Possibly Layer 3* — reason codes describing an operator's internal decline reasons are Layer-3
  candidates and must not be pulled into the protocol by default.

**Contracts affected:** the three OPEN rows above.

**Whitepaper claim:** yes, and it must be honoured — *"The engines produce results and reason codes"*,
and reason codes are listed among what binds a validation to its inputs. The Whitepaper is not edited
in this milestone; this is recorded for its future traceability pass.

**Scope decisions required before writing any rule:**

1. Closed registry, or namespaced-extensible (`banza.*` reserved, `x-vendor.*` free)?
2. Does the vocabulary live in the protocol, or per profile?
3. Versioning and deprecation: does adding a reason code change the protocol version? (ADR-081 already
   sets the precedent that publishing an implicit rule does not.)
4. Is `failed_checks` simply the 13 OTE ids — in which case closing it is a schema change, not a design?

**Remaining gap:** two implementations cannot today agree on what a receipt says, only on its digest.
This is also what blocks the field-level half of **F-07** (semantic equivalence).

### X-05 — Idempotency

The audit recorded this as absent. **It is not absent** — it is partially specified and unevenly
scoped, which is a different problem with a different fix.

**Already published, and normative:**

| Invariant | Statement | Covers |
|---|---|---|
| `INV-IDEM-001` | Every financial write carries a caller-supplied `idempotency_key`; the same key MUST return the existing result without creating a duplicate; **the same key with a different request body MUST be rejected (409), never silently served the first response** | Conflict rule — the part the audit assumed missing |
| `INV-FED-004` | The same `routing_request_id` MUST produce the same result regardless of how many times it is submitted | Cross-operator routing |
| `INV-FED-IDEM-001` | `routing_request_id` is globally unique across all operators and all time | Key scope, federation only |
| `INV-COLLECTION-008` | Collection creation and share-payment are idempotent on the supplied key | Collections, L2 |
| `federation-routing.json` | `routing_request_id` format `rr-<uuid>`, **MUST be stable across retries** | Key format |
| `contracts/events/webhook-types.json`, `webhooks/envelope.schema.json` | Consumers MUST deduplicate on `event.id`; the same event may be delivered more than once | Delivery-side idempotency |

**What is genuinely missing:**

1. **Retention** — how long a key must be remembered. Stated nowhere, for any surface. Without it,
   "the same key returns the same result" has no time bound and two implementations can both conform
   while disagreeing.
2. **Key scope for `INV-IDEM-001`** — per operator, per endpoint, per account? `INV-FED-IDEM-001`
   answers this for federation and nothing answers it for the general write path.
3. **What "a different request body" means** — INV-IDEM-001's conflict rule needs a comparison rule.
   `BCJ/1` now makes one available (digest equality over canonical bytes), which is worth considering
   precisely because it introduces nothing new.
4. **Behaviour on concurrent first-use** of the same key.

**Whitepaper claim:** none. The Whitepaper makes no idempotency claim, so nothing there constrains
the answer.

**Layer question:** `INV-IDEM-001` sits on the operator's own write path, which is the strongest
Layer-3 candidate in this milestone. `INV-FED-004` / `INV-FED-IDEM-001` are cross-operator and
therefore protocol. The classification must be made **before** any rule is written.

### Boundary the next milestone must respect

BANZA must not acquire, as a side effect of closing X-04 and X-05:

- a universal payment state machine;
- settlement or clearing;
- a central ledger;
- a universal error taxonomy;
- universal idempotency semantics.

A semantic enters the protocol only when it is required for **observable interoperability** between
two operators. Everything else stays in Layer 3. The test is not "would this answer a criticism" but
"can two operators interoperate without it".

## 9. Mandatory answers

**Q1 — Was the canonicalization P0 resolved?** **SIM.**

**Q2 — What is the normative canonical representation?**
`spec/canonicalization.md`, identifier **`BCJ/1`**: RFC 8785 (JCS) restricted by profile rules P1–P7
(ADR-082). Declared in force by `contracts/production/protocol-version.json` → `canonicalization.id`.

**Q3 — Which bytes are signed?** `spec/canonicalization.md` §4: take the artifact, remove **only** the
signature member named for that artifact type in §6, verify P1/P2/P3, canonicalize per §2–§3, and sign the
resulting UTF-8 bytes with Ed25519 as-is — no length prefix, no framing, no trailing newline. Every other
member, including unknown ones, is inside the signed bytes.

**Q4 — Which bytes enter the digests?** §5: the same procedure, additionally removing the digest member
itself so it cannot cover itself, then SHA-256, encoded lowercase hex, with no algorithm prefix unless the
field's schema requires one.

**Q5 — Protocol version after remediation, and why?** **1.0.0, unchanged.** No production contract changed
its wire shape; the change is that an unpublished rule became published. A major bump would falsely assert
a broken published contract; a minor bump would falsely assert backward-compatible additive change to
behaviour. Canonicalization carries its own version (`BCJ/1`) so future changes are versioned precisely.
Measured impact confirms the choice: bytes are unchanged for every real artifact and prior signatures still
verify.

**Q6 — Is there now an unambiguous normative-surface manifest?** **SIM** —
`contracts/production/normative-manifest.json`, 138 artifacts with SHA-256, precedence order and explicit
exclusions, each classified by `class` and `tier`. **82 carry tier=implementation** — that is the actual
requirement set; the other 56 are conformance, legal or informative. Digests are verified by the guard,
so the manifest cannot silently go stale.

**Q7 — Is any essential rule still sourced only from code?** **SIM — two, both deferred with rationale:**
the receipt reason-code vocabulary (F-05) and idempotency retention/scope (F-06). Four further cases were
found and closed in the final verification pass — see §6.1 V-1 to V-4, one of which was a second engine
deriving its own canonical bytes. Both are
recorded in §5 and both require a scope decision before specification. No *cryptographic* rule remains
code-sourced.

**Q8 — Are reason codes normatively defined?** **PARCIALMENTE** — five vocabularies are closed
(certification 18 values, revocation-entry 7, root-revocation 4, BRL 2, and the 13 OTE check ids). Three
remain open string arrays: `failed_checks`, and `reason_codes` on both receipt types. See §7 (X-04).

**Q9 — Is idempotency specified where needed?** **PARCIALMENTE** — corrected in the final verification
pass. The audit treated it as absent; it is not. `INV-FED-004`, `INV-FED-IDEM-001` and the `rr-<uuid>`
format rule specify cross-operator routing idempotency, and `INV-IDEM-001` already carries the conflict
rule (same key + different body → 409, never silently served the first response). What is missing is
**retention**, the **key scope** of `INV-IDEM-001`, and what "a different request body" means as a
comparison. See §7 (X-05). **NOT APPLICABLE** for settlement finality and payment lifecycle, which are
Layer-3 by design.

**Q10 — Are the necessary normative states defined?** **PARCIALMENTE** — the validation journey and
certification state machines are published contracts; cross-operator payment execution states remain
Layer 3 by design.

**Q11 — Central BANZA dependency in the transaction/data plane?** **NÃO.**

**Q12 — In the trust/governance plane?** **SIM.** The Key Manifest and BRL are normatively required,
fail-closed, and published at a single canonical `banza.network` origin with no specified alternative. Its
scope is precisely: trust-material distribution and revocation freshness. It is not in the message or funds
path, and it cannot prevent anyone implementing a published version. Recorded as F-08, deferred.

**Q13 — Still legally implementable by third parties?** **SIM** — unchanged and untouched: Apache-2.0
extended to documentation by `NOTICE`, with patent grant; `TRADEMARKS.md` permits "Independent
implementation of the BANZA protocol".

**Q14 — Clean-room readiness?** **NOT READY**, but the blocking profile has changed materially. Five of the
ten clean-room blockers are closed (X-01, X-02, X-03, X-07, X-08) and a sixth is half-closed (X-06). A team
can now implement `BCJ/1` from text, validate it against 24 public vectors, and verify real root,
delegation, metadata, manifest, evidence, registry and revocation signatures against 12 cryptographic
vectors — the whole trust plane — without reading Rust. What blocks it is the **execution** surface: the
reason-code vocabulary (X-04/F-05) and the idempotency rule (X-05/F-06). See the updated package manifest.

**Q15 — "BANZA is a conformance framework, not a protocol" —** **PARCIALMENTE CONFIRMADA**, and less so
than before. The criticism's strongest technical support was that the protocol's most load-bearing rule
lived in the reference implementation; that is now false. What remains is the audit's original, narrower
observation: the evaluation surface is specified to a higher standard than the execution surface, and
closing F-05/F-06 is what would move this to REFUTADA.

## 10. Final verification pass — mandatory answers

**Q1 — Is BANZA still `1.0.0`?** **SIM.** Closed decision, restated at the head of this document. No
alternative version is proposed anywhere in it.

**Q2 — Did this pass find a technical reason making `BCJ/1` inconsistent with the current artifacts?**
**NÃO** for the specification, **SIM** for the implementation of it, now fixed. `BCJ/1` remains
consistent with every artifact: no artifact was found that it rejects, and the byte-identity and
signature-survival evidence stands, now reinforced by `banza-root-ceremony`'s 17 tests passing unchanged
after it was switched to `BCJ/1`. What was inconsistent was the *implementation*: rejection collapsed to
empty bytes (V-1), P3 was unreachable on the production path (V-2), and a second engine derived its own
bytes (V-3). All three are fixed and pinned by tests. **The version does not change:** these are defects
in code and in one specification omission, not changes to the wire form.

**Q3 — Are unknown fields fully subject to `BCJ/1`?** **SIM.** Specified in P4 explicitly, and pinned by
six unit tests and four public vectors covering fractional, exponent, out-of-range at both bounds,
nesting through objects and arrays, and duplicates inside an unknown member.

**Q4 — Does the manifest distinguish normative material from conformance/governance/rationale?** **SIM.**
Two axes, `class` and `tier`; the guard requires both on every artifact and rejects an unknown tier.
Governance and rationale are not in the manifest at all — `not_normative` states that no ADR is required
reading and that no Draft RFC is a requirement of 1.0.0.

**Q5 — How many artifacts does a clean-room implementation actually need?** **82**, of 138 listed:
24 `NORMATIVE_SCHEMA`, 21 `NORMATIVE_CONTRACT`, 18 `NORMATIVE_TRUST_RULE`, 7 `NORMATIVE_SPECIFICATION`,
5 `NORMATIVE_PROFILE`, 4 `NORMATIVE_API`, 3 `NORMATIVE_REGISTRY`. The remaining 56 are 51 conformance,
3 legal, 2 informative.

**Q6 — Must a clean-room team read ADRs to discover current normative behaviour?** **NÃO.** No ADR is in
the manifest and `not_normative` says so. Spot-checked on the load-bearing cases: the canonicalization
rule is in `spec/canonicalization.md`, Model A is restated in `FEDERATION_TRUST_MODEL.md`, and the
canonical discovery path is published in eight `tier=implementation` artifacts — that last one only
became true in this pass, when `conformance/manifests/schema.json` was added (V-5).

**Q7 — Is any Draft RFC required to implement 1.0.0?** **NÃO.** All six BANZA RFCs are Draft; four
federation contracts cite one in `_authority`, and each was checked individually (§6.3). In every case
the rule is carried by the contract or by a `tier=implementation` specification. The citations are a
naming defect, recorded for the next milestone.

**Q8 — Is any normative source of truth still code?** **NÃO.** Zero `_source_of_truth` and zero
`_authority` fields name implementation code; the guard now enforces both fields.

**Q9 — Is canonicalization/signing/trust ready for clean-room?** **READY.** Ten trust-plane capabilities
assessed under the delete-the-Rust test (§6.8); all ten are YES, none dependent on inferred behaviour.

**Q10 — What exactly remains blocking the complete 1.0.0 package?** **X-04 and X-05 — confirmed by
evidence, and both narrower than the audit recorded.** X-04 is three open string arrays, not an absent
taxonomy: five vocabularies are already closed. X-05 is retention, key scope and body-comparison, not an
absent rule: four invariants and a key-format rule are already published, including the conflict rule.
Also open, and lower: X-09 (L4 profile content) and X-10/F-08 (trust-material single origin).

**Q11 — Is this PR ready to merge?** **READY TO MERGE** on technical grounds. All eleven acceptance
criteria in the milestone are met; see §8.
