## 1. Material decisions

### D-1 · The protocol version does not change (ADR-081)

`protocol_version` stays `1.0.0`. No production contract changes its wire shape; what changed is that a
previously unpublished rule became published. Canonicalization is versioned **independently** as `BCJ/1`,
so a future change to it can be versioned precisely without moving the protocol version.

### D-2 · Canonicalization is RFC 8785 restricted by a BANZA profile (ADR-082)

**PROFILE RFC 8785**, not bare adoption and not a bespoke scheme. The profile — integers only within
±(2⁵³−1), duplicate members rejected, unknown members preserved, no Unicode normalisation, UTF-16 member
ordering — is what makes a standard designed for general JSON safe for a protocol that carries money.

The decisive profile rule is **P1 (integers only)**: it removes ECMAScript double formatting, which is the
largest source of cross-language divergence in RFC 8785. This was not a convenience choice — it was
verified first that **zero** `type: number` fields exist in any signed-artifact schema and that BANZA
already mandates integer minor units.

### D-3 · Measured migration impact: none

ADR-081 initially assumed publishing the rule would change bytes and force regeneration of every signed
artifact. **That assumption was tested and is false.** `BCJ/1` and the prior reference behaviour coincide
for every artifact BANZA produces, because they all use ASCII member names, integers in range, and no
floats.

Evidence — `engines/banza-trust/tests/canonical_migration.rs`:

- byte-identity asserted across signed protocol metadata, trust root metadata, operator manifest,
  conformance evidence, public registry entry and the BRL;
- **a signature produced under the prior behaviour still verifies under `BCJ/1`** — which it can only do
  if the signing bytes are unchanged;
- the live Operator Zero artifact was checked independently: 19 members, all-ASCII names, all integers
  within the safe range.

No artifact required regeneration. The transition is a specification change, not a data migration.

## 2. Cryptographic impact

| Aspect | Before | After |
|---|---|---|
| Rule location | `engines/banza-trust/src/lib.rs` (`serde_json::to_string`) | `spec/canonicalization.md` (normative), implemented by the engine |
| Language coupling | Total — the norm was one crate's serializer | None — the rule is text, with vectors |
| Member ordering | UTF-8 byte order (incidental `BTreeMap` default) | UTF-16 code units, stated (P6) |
| Numbers | Whatever `serde_json` emits (`100.0`, `1e+22`) | Integers only, safe range, rejected otherwise (P1/P2) |
| Duplicate members | Parser-dependent (last-wins) | Rejected, fail-closed (P3) |
| Unknown members | Undefined | Preserved and signed (P4) |
| Unicode | Undefined | Not normalised; publishers emit NFC (P5) |
| Bytes produced for real artifacts | — | **Identical** (§1 D-3) |

**Cross-implementation evidence.** The public vectors were generated by an implementation written from the
specification text, with no shared code with the engine; `engines/banza-trust/tests/canonicalization_vectors.rs`
asserts the Rust engine reproduces all 20 (14 accept + 6 reject) exactly, including the digest and byte
length of each. Two independent implementations agreeing is the evidence that the rule now lives in the
specification rather than in either implementation.

## 5. Remaining work, with rationale

Four findings are deferred rather than closed, and each is deferred for a stated reason rather than for
convenience:

- **F-05 (reason codes)** and **F-06 (idempotency)** both require a *scope decision first* — the milestone
  itself (§24) requires classifying each subject as protocol-normative, profile-normative, Layer 3, or
  implementation-internal before specifying it. Specifying them without that classification is exactly the
  "import requirements from other systems" failure the milestone forbids.
- **F-07 (semantic equivalence)** is now half-closed: the digest-level foundation is specified and
  vector-backed. The field-level rule depends on F-05, because "equivalent reason codes" cannot be defined
  before the reason-code model is.
- **F-08 (trust-plane origin)** is a genuine architectural decision, not a documentation gap. The milestone
  (§36) explicitly permits recording it as a future consideration rather than implementing federated
  distribution because it is possible.

These are the substance of the next milestone. **The audit's P0 is closed and does not reappear in it.**

## 7. Mandatory answers

**Q1 — Was the canonicalization P0 resolved?** **SIM.**

**Q2 — What is the normative canonical representation?**
`spec/canonicalization.md`, identifier **`BCJ/1`**: RFC 8785 (JCS) restricted by profile rules P1–P7
(ADR-082). Declared in force by `contracts/production/protocol-version.json` → `canonicalization.id`.

**Q3 — Which bytes are signed?** `spec/canonicalization.md` §4: take the artifact, remove **only** the
signature member named for that artifact type in §6, verify P1/P2/P3, canonicalize per §2–§3, and sign the
resulting UTF-8 bytes with Ed25519 as-is — no length prefix, no framing, no trailing newline. Every other
member, including unknown ones, is inside the signed bytes.

**Q4 — Which bytes enter the digests?** §5: the same procedure, additionally removing the digest member
itself so it cannot cover itself, then SHA-256, encoded lowercase hex, with no algorithm prefix unless the
field's schema requires one.

**Q5 — Protocol version after remediation, and why?** **1.0.0, unchanged.** No production contract changed
its wire shape; the change is that an unpublished rule became published. A major bump would falsely assert
a broken published contract; a minor bump would falsely assert backward-compatible additive change to
behaviour. Canonicalization carries its own version (`BCJ/1`) so future changes are versioned precisely.
Measured impact confirms the choice: bytes are unchanged for every real artifact and prior signatures still
verify.

**Q6 — Is there now an unambiguous normative-surface manifest?** **SIM** —
`contracts/production/normative-manifest.json`, 130 artifacts with SHA-256, precedence order, and explicit
exclusions. Digests are verified by the guard, so the manifest cannot silently go stale.

**Q7 — Is any essential rule still sourced only from code?** **SIM — two, both deferred with rationale:**
the reason-code vocabulary (F-05) and the idempotency conflict/retention semantics (F-06). Both are
recorded in §5 and both require a scope decision before specification. No *cryptographic* rule remains
code-sourced.

**Q8 — Are reason codes normatively defined?** **PARCIALMENTE** — a closed 18-value enum exists for
certification records; the receipt-level vocabulary remains an open string array (F-05, deferred).

**Q9 — Is idempotency specified where needed?** **NÃO** for cross-operator routing (F-06, deferred).
**NOT APPLICABLE** for settlement finality and payment lifecycle, which the audit confirmed are Layer-3 by
design with the boundary explicitly stated.

**Q10 — Are the necessary normative states defined?** **PARCIALMENTE** — the validation journey and
certification state machines are published contracts; cross-operator payment execution states remain
Layer 3 by design.

**Q11 — Central BANZA dependency in the transaction/data plane?** **NÃO.**

**Q12 — In the trust/governance plane?** **SIM.** The Key Manifest and BRL are normatively required,
fail-closed, and published at a single canonical `banza.network` origin with no specified alternative. Its
scope is precisely: trust-material distribution and revocation freshness. It is not in the message or funds
path, and it cannot prevent anyone implementing a published version. Recorded as F-08, deferred.

**Q13 — Still legally implementable by third parties?** **SIM** — unchanged and untouched: Apache-2.0
extended to documentation by `NOTICE`, with patent grant; `TRADEMARKS.md` permits "Independent
implementation of the BANZA protocol".

**Q14 — Clean-room readiness?** **NOT READY**, but the blocking profile has changed materially. Five of the
ten clean-room blockers are closed (X-01, X-02, X-03, X-07, X-08) and a sixth is half-closed (X-06). A team
can now implement `BCJ/1` from text, validate it against 20 public vectors, and verify real root,
delegation, metadata, manifest, evidence, registry and revocation signatures against 12 cryptographic
vectors — the whole trust plane — without reading Rust. What blocks it is the **execution** surface: the
reason-code vocabulary (X-04/F-05) and the idempotency rule (X-05/F-06). See the updated package manifest.

**Q15 — "BANZA is a conformance framework, not a protocol" —** **PARCIALMENTE CONFIRMADA**, and less so
than before. The criticism's strongest technical support was that the protocol's most load-bearing rule
lived in the reference implementation; that is now false. What remains is the audit's original, narrower
observation: the evaluation surface is specified to a higher standard than the execution surface, and
closing F-05/F-06 is what would move this to REFUTADA.
