# Implementing BANZA L0 — Protocol Sandbox

> **Derived informative view. The BANZA Normative Manifest remains authoritative.**
>
> This page is a **map, not a specification**. It states no requirement of its own. Every obligation
> below is followed by the normative artifact that imposes it, and that artifact governs. If this guide
> and a normative artifact ever disagree, the artifact is right and this guide is the defect.

---

## 1. What you are implementing

L0 — **Protocol Sandbox** — is the smallest complete statement of BANZA: represent money as integers
correctly, produce a valid manifest, canonicalize deterministically, and use published reason codes.

You are not building a payment product at L0. You are demonstrating that your implementation
*represents the protocol correctly* in a controlled environment.

**Source:** [`contracts/production/conformance-profiles.production.json`](../../contracts/production/conformance-profiles.production.json), profile `L0`.

## 4. Canonical JSON — BCJ/1

BANZA canonicalization is a **profile of RFC 8785 (JCS)**. Read
[`spec/canonicalization.md`](../../spec/canonicalization.md) in full; it is short and every rule in it
is load-bearing. In outline, the profile adds to JCS:

- integers only, bounded by ±(2⁵³−1)
- duplicate member names rejected rather than resolved
- unknown members preserved, and fully subject to the profile
- no Unicode normalisation
- rejection is an error, never an empty result

That last point is the one implementations get wrong. A document the profile rejects has **no**
canonical form; it must not be treated as canonicalizing to empty bytes, because two different invalid
documents would then share a digest.

**Verify against:** [`conformance/vectors/canonicalization.json`](../../conformance/vectors/canonicalization.json).

## 5. Discovery

L0 requires no discovery surface of its own. Where an implementation does publish one, the canonical
locations are `.well-known/banza/operator.json` and `.well-known/banza/signed-protocol-metadata.json`
(ADR-029) — but publishing those is first **required** at L3, not L0.

## 6. Identity and trust

**L0 requires none.** No signing key, no key manifest, no published metadata, no identity of any kind.
Trust material enters at L3.

This is worth stating plainly because it is the most common wrong assumption about L0: there is nothing
to register, nobody to ask, and no credential to obtain.

## 7. L0 contracts

One: the **operator manifest**
([`contracts/production/operator-manifest.production.schema.json`](../../contracts/production/operator-manifest.production.schema.json)),
validated structurally against
[`conformance/manifests/schema.json`](../../conformance/manifests/schema.json), declaring capabilities
per [`conformance/capabilities/schema.json`](../../conformance/capabilities/schema.json) and the
environment as `simulated`.

`MON-001` — monetary integer representation — applies to every monetary value your implementation
handles. It is defined in [`contracts/invariants.json`](../../contracts/invariants.json), and it is the
only invariant L0 requires. It is also the one that is hardest to retrofit: an implementation that
represents money as a floating-point number anywhere cannot reach L0 without changing that.

## 8. Error and reason semantics

[`spec/reason-codes.md`](../../spec/reason-codes.md) governs. The rule that shapes an implementation
most is its first: **a status decides, a reason code explains.** A reason code never carries the
outcome; it says why the outcome was what it was.

Codes come from the published vocabularies in
[`contracts/production/reason-code-registry.production.json`](../../contracts/production/reason-code-registry.production.json).
Vendor extensions use `x-<vendor>.<code>` and never collide with core codes.

**Verify against:** [`conformance/vectors/reason-codes.json`](../../conformance/vectors/reason-codes.json).

## 8b. Declaring capabilities

L0 requires **no** capability, so nothing here is an obligation at this level. It is stated because the
rule is easy to get wrong at L1 and the machinery is already in your set.

The core capability identifiers are published in
[`contracts/production/capability-registry.production.json`](../../contracts/production/capability-registry.production.json),
and [`spec/capabilities.md`](../../spec/capabilities.md) governs them. Two consequences worth knowing
before you build anything:

- To satisfy a profile's capability requirement you declare the **canonical identifier** in your
  manifest's `capabilities` array. Other strings may appear there — the member is not a closed enum —
  but they satisfy nothing.
- Comparison is **exact**. No case folding, no `_` ↔ `-` substitution, no plural guessing, no prefix
  matching. `consumer-payment` is not `consumer_payment` unless the registry says it is, and it does
  not.

The `supports_*` booleans of the capabilities schema are a separate, older vocabulary. Each was audited
against the core capabilities and exactly one relation came out **exact**; the rest are broader,
narrower or unrelated, and none of those satisfies a capability requirement.

## 9. Public vectors

Four vector files, all self-contained. **Which cases apply to L0 is stated in the profile registry**
under `required_vector_cases` — listing a file is not the same as requiring all of it:

| Vectors | Cases required at L0 | What passing them demonstrates |
|---|---|---|
| `canonicalization.json` | all 24 | Your canonical form is byte-identical to the profile's, and your rejections are rejections |
| `operator-manifests.json` | all 4 | You accept valid manifests and refuse invalid ones for the stated reason |
| `reason-codes.json` | **9 of 21** — RC-001, RC-002, RC-004–RC-009, RC-014 | Your codes are well-formed and drawn from the published vocabularies |
| `capabilities.json` | all 12 | A declaration satisfies a requirement only when the registry says it does |

The twelve reason-code cases **not** required at L0 concern `failed_checks`, `trust_status`, receipt
equivalence and per-step engine statuses. Those arise in trust evaluation, which begins at L3. You do
not need them here, and the registry says so rather than leaving you to infer it.

They are data. Running them requires no BANZA code — see
[`conformance/package/`](../../conformance/package/README.md), which is the same material packaged to
be consumed outside this repository.

## 10. Evidence and output

At L0 you should be able to produce, for your own implementation:

- the canonical bytes and SHA-256 digest of any document you handle
- a manifest that validates, and a stated reason when one does not
- a per-vector pass/fail record

L0 needs no signature over that evidence and no publication of it. Signed evidence bundles begin at L3.

## 11. What is **not** required for L0

Directly from the profile registry, `not_required`:

- Live payment rails of any kind
- Wallets, transfers or a ledger — those are **L1**
- Payment requests, QR or instant execution — those are **L2**
- Federation, cross-operator routing or settlement — those are **L3**
- External payment-network integration — that is **L4**
- Trust material of your own: no signing key, no key manifest, no published metadata
- Any registration, submission, approval or credential from any party

This list is normative in the registry, not in this guide. It exists because an implementer who cannot
tell where a level *stops* will implement more than the level asks.

## 12. The next profile, and how the levels are shaped

**L1 — Core Payment Capability** adds 17 artifacts: wallets, transfers, the ledger, events,
traceability and idempotency, with ten further invariants.

The five levels are not all shaped the same way, and an implementer should know that before
planning:

| | Shape |
|---|---|
| **L0** | The base. Everything else includes it |
| **L1 · L2 · L3** | **Universal normative increments.** Each adds a fixed set of artifacts, invariants and capabilities that every implementation at that level satisfies. What to build is fully determined by the registry |
| **L4** | **A mechanism, parameterized by an external profile.** It inherits all of L3 and adds *no universal artifact of its own*. Its additional requirements come from the external-interoperability profile an implementation selects |

**Reaching L3 does not reach L4.** Because L4 adds no universal artifact, the derived tables show its
incremental set as zero — and that zero is easy to misread. An implementation that satisfies L3 has
satisfied *none* of L4's requirements, because it has selected no external profile, identified no
external network, and produced no external-integration evidence. With no profile selected, the
published per-level result for L4 is `not_run` — not `pass`.

BANZA 1.0.0 publishes **no concrete external-interoperability profile**. The mechanism is defined;
nothing currently exercises it, so there is no executable L4 demonstration today. That is stated rather
than filled with an example, because an invented profile would make the mechanism look demonstrated
when it is not.

Whether an L4 integration can be demonstrated without touching the live external network is a property
of the profile selected, not of L4. A profile may define evidence producible in a test environment
where the external counterparty is represented faithfully enough; BANZA makes no universal ruling
either way, having no basis for one.

See [`docs/derived/implementation-sets.md`](../derived/implementation-sets.md) for the per-level
increments, and the profile registry for what each one requires.

## A note on effort

This guide states what the surface asks for. It does not estimate how long implementing it takes, and
no number in it should be read as a claim about difficulty. **No independent implementation of BANZA
has been demonstrated**, so the real effort is unmeasured — and until someone outside this repository
implements L0 from these documents alone, it remains unmeasured.
