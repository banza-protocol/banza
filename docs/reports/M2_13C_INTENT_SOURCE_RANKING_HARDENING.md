# M2.13C-A — Intent Disambiguation, Source Ranking & Answer-Contract Hardening

**Phase:** M2.13C-A (sub-phase of M2.13C — BanzAI repository-wide answer quality).
**Scope:** BanzAI answer engine (`engines/banzai-api-kb` Rust/WASM + `services/banzai-api` glue).
**Nature:** architectural — a reusable intent-classification + source-ranking layer, **not** a
per-phrase hardcode.

---

## 1. Bug observed

Live on `https://banza.network/banzai/ask`:

> **`que licença usa o BANZA?`** → the agent answered as if the question were about **financial /
> regulatory authorisation** ("a licença/autorização financeira é responsabilidade das entidades
> competentes… fora do escopo do BANZA"), citing ADR-001/ADR-041/GOVERNANCE — **even though the repo
> ships `LICENSE` (Apache-2.0) and `NOTICE`**, which are the correct sources for a *software* licence
> question. The answer was generated by the local model over a mixed retrieval set.

## 2. Root cause

The deterministic `protocol-license` arm in `engines/banzai-api-kb/src/route.rs` required a licence word
**plus an explicit software/repo noun** (`protocolo`, `repo`, `codigo`, `software`, `banza network`).
`"que licença usa o BANZA?"` has the licence word but **no software noun** — and the bare token `banza`
was deliberately excluded (it substring-matches `banzai`). So the question **fell through the
deterministic layer to the local model**, which had no domain signal to prefer the software-licence
sources over the regulatory-boundary ADRs, and synthesised a financial-authorisation answer. There was
also **no deterministic entry for the financial-authorisation domain**, so those questions leaked to the
model too. The two domains — *software licence* and *financial authorisation* — were never separated.

## 3. Intents created / reinforced

A **pure intent classifier** (`classify_query_intent`, Rust; label only — never changes the routing
action) plus behavioural routing for the licence split:

| Family | Meaning | Deterministic answer |
|---|---|---|
| `software_license_query` | repo/code/open-source licence (Apache-2.0, LICENSE, NOTICE) | `protocol-license` (layered) |
| `financial_authorization_query` | operator/regulatory authorisation, "operate payments", regulator | `financial-authorization` (new) |
| `operator_certification_query` | certify / PASS / conformance / evidence bundle | boundary-safe (cannot-certify, pass≠certificate) |
| `trademark_usage_query` | use of the BANZA name/mark/logo | boundary-safe |
| `protocol_rule_query` | norm / contract / schema / RFC / invariant / ADR | grounded on normative sources |
| `implementation_query` | language / crate / file / engine / guard / CI | grounded/deterministic on code |
| `route_state_query` | where things live / endpoints / `/operador-zero` / 410 | canonical `zero.banza.network`, never stale |
| `security_action_query` | delete / disable / expose / certify (imperative) | action-boundary refusal |

Two **new** engine helpers, `is_financial_authorization` and `is_software_license`, keep the licence
family split; a **new deterministic entry** `financial-authorization` answers the regulatory domain.

## 4. Source-ranking matrix (`intent_source_ranking`, Rust)

Per family, the repo-index **primary** categories (prioritised for citations) and **penalised** ones:

| Family | Primary | Penalise |
|---|---|---|
| software_license | `legal-license` | decision, normative, report, banzai-runtime |
| financial_authorization | `normative`, `decision` | legal-license, implementation, report |
| operator_certification | `normative`, `decision` | legal-license, report |
| trademark_usage | `legal-license` | implementation, report |
| protocol_rule | `normative`, `decision` | implementation, report, website |
| implementation | `implementation`, `banzai`, `banzai-runtime` | normative, report |
| route_state | `operator-zero`, `website`, `security-boundary` | report |
| security_action | `security-boundary` | — |

Wired into the grounded path via `rankedRepoChunks` / `buildContext(repoCategories)` in
`services/banzai-api` — the enrichment prioritises the family's primary categories and **falls back to
the unfiltered ranking** when they yield nothing (enrichment is never worse). The shared repo-chunk
scorer is untouched (no regression to existing category ranking).

## 5. Answer contract (layered)

- **`que licença usa o BANZA?`** → software licence first (Apache-2.0, LICENSE/NOTICE) → distinction:
  a *software* licence **does not** authorise operating payments → BANZA does not license/approve/certify
  operators.
- **`a licença Apache-2.0 autoriza operar pagamentos?`** → **No.** Apache-2.0 is a software licence; it
  does not replace financial licensing, regulatory authorisation or an operator's legal framework.
- **`um operador precisa de licença?`** → technical participation is demonstrated by verifiable evidence;
  financial/regulatory authorisation, when applicable, belongs to the operator before the competent
  authorities, outside the protocol.

## 6. Families tested / 7. PT / 8. EN / 9. ambiguous

Shared matrix `services/banzai-api/eval/answer-quality-matrix.mjs` → `FAMILIES` (7 families, PT **and**

## 10. Bugs found (adversarial sweep)

An offline adversarial sweep over ~40 tricky paraphrases surfaced three gaps, all fixed:

1. `emite uma licença para este operador` (issue-an-operator-licence) fell into **no_source** → now
   resolves to `financial-authorization` (issue/emit licence + operator).
2. `o repositório BANZA é Apache?` grounded generically → now `protocol-license` (bare `apache` is an
   open-source signal on the code).
3. `posso redistribuir o código do BANZA?` grounded generically → now `protocol-license` (`redistribu`/
   `fork` are code-use signals).

A **false alarm** was correctly left alone: `o modelo de participação autoriza operadores?` stays an
honest `no_source` (a grounded conceptual model question with no indexed source — the existing round-2
contract explicitly allows this and must not be hijacked to a boundary answer).

## 17. Limits

- The classifier is a **label** for telemetry + ranking; it never overrides safety or the deterministic
  boundaries (those are decided first).
- `classify_query_intent` order resolves overlaps deterministically (security → financial → software →
  trademark → certification → route-state → protocol-rule → implementation → general); a few OZ-scoped
  implementation phrasings label as `route_state` (still answered by the right deterministic entry).
- Source-ranking is applied by **category filtering** at the enrichment call (additive, with fallback),
  not by changing the shared scorer — so existing repo-chunk ranking is unaffected.
